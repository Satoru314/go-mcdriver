# go-mcdriver 設計書

Minecraft Java Edition 1.21.4 に、bot をユーザーとしてログインさせ、そのユーザーから情報を得て、行動を指示できる Go のライブラリ。
街づくり bot（[minecraft-ai-town](https://github.com/Satoru314/minecraft-ai-town)）の土台として作るが、それ単体で使える道具にする。
ここには、ユーザーが了承した内容だけを書く。

## 方針

- Go で書く。既存の bot ライブラリ（mineflayer など）に頼らず、通信からゼロから作る
- 対象のバージョンは 1.21.4 に固定する
- 「体と感覚」までを持ち、考えて動く部分（経路探索、クラフトの手順、建築、判断）は使う側に置く

## 機能

### 接続

- ログインし、接続を保つ
- ログインはオフラインモード（正規アカウントの認証なし）だけに対応する。通信の暗号化は作らない

### センサー（ゲームから得る情報）

1. 自分の体: 位置、向き、地面に立っているか、HP、満腹度、経験値、死亡とリスポーン、サーバーからの位置の強制修正
2. 周りの地形: チャンク（ブロックの種類と状態）、ブロックの変化、明るさ
3. 周りの生き物と物: 出現と消滅、位置と動き、種類と状態（プレイヤー、モブ、落ちているアイテム）
4. 持ち物: 自分の持ち物と変化、開いた容器（チェスト、かまど、作業台）の中身、操作がサーバーに受け入れられたか
5. 世界の状態: 時刻、天気

### 物理

- 重力、衝突、水などの物理を持ち、毎ティック、サーバーに正しい位置を送る

### アクチュエーター（低レベルの行動）

- 向きを変える、歩く、走る、ジャンプ
- ブロックを掘る、置く。置くときは、向く方角（階段・ドアの向き）と、面のどこを指すか（ハーフブロックや階段の上下）を指定できる
- ブロックを使う（ドア、ベッド、容器を開ける）
- アイテムを使う（食べる など）。使い続ける・離す（弓を引いて放つ）
- 持ち物の操作（スロットのクリック、持ち替え、捨てる）
- 生き物を攻撃する。攻撃の溜め時間（今攻撃すれば全力か）が分かる
- 死んだあとにリスポーンする
- 開いている容器を閉じる

### 作り

- ライブラリが内部で毎ティック物理を計算し、位置をサーバーに送る。使う側は移動の状態（前後左右、ジャンプ、走る）をセットする
- 時間のかかる行動は `context` を受け取り、時間切れや中止で必ず戻る
- 状態を読む関数は呼んだ時点の写しを返し、複数の goroutine から同時に呼べる
- 入力と出力は、必要に応じて構造体にする
- ブロックとアイテムのデータ（硬さ、適した道具、当たり判定の形、レシピ、食べ物）は、サーバーの jar の公式データ出力から作る
- 地形は、1ブロックずつ読む `Block()` のほかに、範囲をまとめて写し取る読み方（`WorldView`）を用意する（経路探索で大量に読むため）
- アイテムの部品情報（data components: 耐久値、エンチャントなど）は使う側に出さない。通信を正しく読み進めるために、中で読み飛ばすだけにする

## リポジトリとファイル分け

- 独立した公開リポジトリ `github.com/Satoru314/go-mcdriver`（Go モジュール）にする。使う側は `go get` で取り込む
- パッケージ名は `mcdriver`（使う側は `mcdriver.Connect(...)` のように書く）
- 使う側が触るのはルートのパッケージと `data/` だけ。それ以外は `internal/` に置く

```
go-mcdriver/
├── client.go        Connect, Close, Done, Err, Config。毎ティックの処理の本体
├── geom.go          BlockPos（整数の座標）, Face（6方向）
├── self.go          Self（位置, 速度, 向き, 接地, HP, 満腹度, 経験値, 死亡）
├── world.go         Block, Light, WorldView（地形を読む）
├── entities.go      Entity, Entities（生き物と落ちているアイテム）
├── inventory.go     Inventory, Item, Container, ClickSlot, SelectHotbar, Drop, CloseContainer
├── controls.go      Controls, SetControls, Look, LookAt
├── actions.go       Dig, Place(PlaceOpts), UseBlock, StartUseItem / StopUseItem, Attack, AttackCharge, Respawn
├── events.go        Event の種類と Events()
├── time.go          Time, Weather
├── data/            ブロック・アイテム・レシピ・食べ物の情報（*_gen.go は公式データから自動生成）
├── internal/
│   ├── protocol/    パケットの枠, 圧縮, 基本の型（ゲームのことは知らない）
│   ├── conn/        接続, ログインと設定の流れ
│   ├── packets/     パケットごとの読み書き
│   ├── nbt/         NBT の読み込み
│   ├── chunk/       チャンクの展開（ブロックの並び, 明るさ）
│   ├── physics/     プレイヤーの物理, 当たり判定
│   └── state/       受け取った状態の保管（鍵をかけて、写しを返す）
└── cmd/
    ├── gendata/     サーバーの jar から公式データを書き出し、data/*_gen.go を作る
    └── mcprobe/     接続して状態を表示するだけの確認用ツール
```

依存の向き: `protocol` はゲームのことを知らない。`physics` は `data` と `chunk` を使う。ルートのパッケージはそれらを組み合わせて外に見せる。

## テスト

### 正しさの確かめ方

1. 部品ごとのテスト: 通信の基本の型や NBT は仕様のバイト列と照らし合わせる。チャンクの展開は本物のサーバーから受け取ったデータで確かめる
2. テスト用サーバーでの実地テスト: ドライバで行動し、結果をサーバーの RCON で確かめる。テスト中にサーバーからの位置の強制修正が1回も起きないことを合格の条件にする
3. 長時間の連続運転: 切断、強制修正、メモリの増え方を見る。本番の bot に使うのはこれに通ってから

### テスト用サーバー

- `go test` が、Docker でテスト用の Paper 1.21.4 を1つ起動する（平らなワールド、時間と天気を止める、敵が勝手に湧かない）
- テストはできるだけ並列で動かす。テストごとに専用の区画と専用の bot 名を割り当てる。準備と確認は RCON で行う
- 時刻や天気など、ワールド全体に効くものを変えるテストだけは1つずつ動かす
- Docker は開発用コンテナ（CT102）で動かす（入れ子の設定 nesting を有効にする）。本番サーバー（CT903）には触らない
- テスト用サーバーは起動したままにし、テストはそこに繋ぐ（毎回の起動待ちをなくす）
- テストで開発を止めない: すぐ終わる部品ごとのテストは手元でいつでも回し、時間のかかる実地テストは裏で回して結果だけ受け取る

### CI

- テストは基本的にローカルで行う
- GitHub Actions も組む（push したときの確認。Actions の中で Paper を起動して実地テストもできる）

## 座標とベクトル

| 用途 | 使うもの |
|---|---|
| 位置、速度 | gonum の `spatial/r3` の `r3.Vec` |
| 当たり判定 | gonum の `spatial/r3` の `r3.Box` |
| ブロックの位置 | 整数の x, y, z を持つ自前の小さな型（小数から変換するときは下に丸める） |

- 座標系は Minecraft に合わせる（+x が東、+z が南、+y が上）


## 開発の進め方

- Claude は実装そのものではなく、開発用のプロセス（開発係の Claude）を立てて管理する
- 開発係は別々の tmux セッションで動かし、それぞれ別の作業ブランチ（git worktree）で作業させる
- Claude は作業の割り振り、進み具合の確認、テスト結果の確認、取り込み、ユーザーへの報告をする

### ドライバの実装の順番

| # | 単位 | 中身 | 合格の条件（テスト） |
|---|---|---|---|
| 0 | 土台 | リポジトリ、Go、Docker（CT102 の入れ子設定と再起動）、テスト用サーバーを立てる仕組み、RCON の補助 | テスト用サーバーが立ち上がり、RCON でコマンドが通る |
| 1 | 公式データ | サーバーの jar からデータを書き出し、`data/` を生成する | 生成した数が公式データと一致する。いくつかを抜き取って確認（石の硬さ、樫の階段の状態など） |
| 2 | 通信の基本 | VarInt、文字列、座標、パケットの枠、圧縮 | 仕様のバイト列と一致する（部品ごとのテストのみ） |
| 3 | ログイン | ハンドシェイク、ログイン、設定、ゲーム開始、接続の維持 | bot が入り、RCON の `list` に出る。60秒たっても切られない |
| 4 | 地形 | NBT、チャンクの展開、ブロックの変化、明るさ、`WorldView` | RCON で置いたブロックと `Block()` の結果が一致する |
| 5 | 自分の体 | HP、満腹度、経験値、位置の同期、死亡、リスポーン | RCON でダメージを与える・倒す → 値の変化とリスポーンが正しい |
| 6 | 生き物 | 出現、消滅、移動、状態 | RCON で出したモブの位置と種類が一致する |
| 7 | 物理と移動 | 歩く、走る、ジャンプ、落下、水、階段、向き | 位置がサーバーの記録と一致する。強制修正が0回 |
| 8 | 持ち物 | スロット、部品情報の読み飛ばし、クリック、持ち替え、捨てる、容器の開閉 | `/give` で渡した物が持ち物に出る。チェストとの出し入れが合う |
| 9 | 行動 | 掘る、向きを指定して置く、使う、食べる、弓、攻撃と溜め時間 | 結果を RCON で確認（ブロックが消えた、階段の向きが合う、ゾンビを倒せた など） |
| 10 | 仕上げ | イベント、時刻と天気、長時間運転、設計書の移植、CI | 数時間動かして、切断、強制修正、メモリの増え方に問題がない |

- 3 が終われば、4・5・6・8 は並行して進められる
- 7（物理と移動）は 4（地形）と公式データが必要なので、そのあと。9（行動）はほぼ全部がそろってから

### テストを回す場所

- 部品ごとのテスト（数秒）: 開発係が作業中にいつでも回す
- 実地テスト: CT102 の Docker のテスト用サーバー（起動したまま）で、裏で回す。単位ごとの合格判定はここで行う
- CI: push したときに GitHub Actions で全部を回す

### テストが失敗したとき

- 開発係はその作業をその場で止める。自分で直して先に進まない
- 開発係は失敗の記録（どのテストか、期待した値と実際の値、ログ、関係するパケットの記録、原因の予想）を書いて Claude に渡す
- 直し方は Claude（管理役）が決める（2026-10-27 からユーザーが任せた）。決めた内容と理由はユーザーに報告する
- 失敗していない、ほかの単位の作業は止めずに進める
